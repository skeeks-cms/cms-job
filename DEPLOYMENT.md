# Развёртывание воркеров

## Требования и проверка установки

Ядро объявляет только `default` и `maintenance`. Предметные полосы добавляет
пакет, который реализует задания, через свой общий конфиг:

```php
return [
    'components' => [
        'jobQueueFactory' => ['queues' => ['hosting' => []]],
        'jobRegistry' => ['types' => [/* реальные типы заданий пакета */]],
    ],
];
```

Проект переопределяет настройки поверх конфигов пакетов. Полоса не запускает
воркер автоматически: примеры ниже для `imports`, `hosting` и других полос
применимы только после регистрации их потребителем. Таймаут и повторы задаются
у типа задания; TTR сообщения равен `timeout + leaseSeconds`, а `queues.*.ttr`
не является общим лимитом задач. При обновлении ранней dev-версии перенесите
используемые предметные полосы в конфиги потребителей до перезапуска воркеров.
История и сообщения из БД не удаляются.

Пакет требует CMS `^6.4.9.25` (либо явно выбранный `dev-master`) с явной
регистрацией миграций. Нативные миграции yii2-queue не подключать:
схемой `cms_queue` владеет cms-job. При обновлении CMS также обновить
установленные cms-admin, cms-comments и cms-hosting до версий с регистрацией
миграций. Новые Composer-метаданные должны попасть в план Yii Config.

Проверенная среда этого этапа: PHP 8.2, MariaDB 10.5, yii2-queue 2.3.8.
`tests/job-release-install.php` проверяет миграции пакета в отдельной MariaDB
с минимальными таблицами CMS для внешних ключей, а не установку всей CMS.
Варианты: без аргументов — новая схема, `--upgrade` — старые четыре миграции
и сохранение истории, `--collision` — отказ принять неизвестную cms_queue.
Каждый вариант проверяется без префикса и с `SKEEKS_JOB_RELEASE_PREFIX=sx_`.
Проверяются две полосы ядра и шесть полос тестового потребителя через реальные изолированные дочерние процессы,
атомарность постановки, подтверждение доставки и старый маршрут cmsJob.

Тест требует отдельного disposable-контейнера `cmsjob-release-db` во внутренней
сети PHP, с MariaDB 10.5 и пустым root-паролем только для этого контейнера.
Не публикуйте его порт наружу и не подключайте том БД сайта. Тест создаёт и
удаляет только собственную случайную БД `cmsjob_release_<hex>`; после теста
удалите временный контейнер. Это не проверка чистого Composer install.

Для проверки чистых зависимостей скопируйте
`tests/fixtures/install-project/composer.json` в **отдельный пустой каталог**
внутри PHP-контейнера и выполните там `composer install --no-interaction`.
Path-репозиторий копирует кандидат cms-job из `/shared-vendor`; остальные
пакеты устанавливаются из опубликованных версий. Не выполняйте эту операцию
в каталоге рабочего сайта. `SKEEKS_APP_ROOT=<каталог>` переключает тесты на
этот vendor. Затем запустите `tests/job-composer-config.php` установленного
cms-job для проверки сгенерированного плана конфигурации.

`tests/job-release-install.php --regression` запускает шесть регрессионных
тестов в дочерних процессах на своей временной БД без префикса. В этом режиме
ни родитель, ни дочерние воркеры не читают конфигурацию БД сайта. Используются
минимальные FK-таблицы и fixture-таблица cms_agent: это не проверка миграций
всей CMS/агентов или загрузки файлов в реальное хранилище.

Мост расписания требует версии cms-agent с `CmsAgentModel::pushJob()` и
миграцией `m260822_220000__alter_table__cms_agent__job_type`. Опубликованная
версия `3.1.0.1` их не содержит. Ядро и ручные задания от этого не зависят;
релиз интеграции с расписанием требует отдельного выпуска cms-agent и
повторного прогона на его опубликованной версии. Отсутствующий мост является
ошибкой регрессионного прогона, а не молча пропущенным успешным тестом.

## Переход со старого транспорта

До выкладки нового кода остановите создание заданий, включая расписание.
На старой версии дождитесь завершения очереди и работающих заданий; ненужные
операции отмените явно штатным механизмом. Затем остановите старые воркеры,
сделайте резервную копию, обновите код/зависимости и выполните миграции.

Миграция fencing откажется работать при наличии `queued` или `running` до
изменения схемы. Старый транспорт хранил очередь прямо в `cms_job_run`;
создание пустой cms_queue без этой проверки оставляло бы задания без доставки.
Автоматически повторять внешние операции при обновлении небезопасно.

Если cms_queue уже существует, но миграция её создания отсутствует в истории,
обновление остановится для проверки схемы и данных. Не удаляйте таблицу и не
помечайте миграцию выполненной без проверки. MariaDB DDL не откатывается
транзакцией целиком, поэтому частично применённую схему нужно разбирать явно.

## Обновление работающих воркеров

При обновлении пакета перезапустите **все** воркеры после завершения текущих
операций. Родитель и дочерний процесс должны использовать одну версию кода:
внутренний `worker/exec` получает уникальный токен попытки от родителя.
PID используется только для диагностики, не для проверки владения.

DB-доставка допускает повтор после аварии. Это не бизнес-повтор: лимиты
`maxAttempts` и разрешение повторного выполнения задаёт тип задания.
При аварии до захвата та же транспортная строка освобождается с задержкой
`jobConsumer.crashRedeliveryDelay` (30 секунд по умолчанию). Пока причина
загрузочной ошибки не устранена, операция остаётся ожидающей; ошибки воркера
нужно отслеживать в журнале `skeeks/job`.

После аварии уже захваченного задания требуется периодический
`php yii cms-job/worker/reap`: идемпотентные операции восстанавливаются,
неидемпотентные получают `timed_out`. Слепой перепубликации всех `queued` нет.

### Регрессионные проверки

На тестовой БД выполните все `tests/*-smoke.php`,
`tests/job-transport-integration.php` и `tests/job-recovery-regression.php`.
Последний использует отдельный канал и тестовую точку входа, общую для
родителя и детей; проверяет аварии до/после захвата, реальные TTR, повторы,
двух воркеров и SIGTERM. Проверка уборщика откажется работать, если обнаружит
чужие просроченные запуски. Старые интеграционные тесты используют обычные
полосы: запускайте их только на пустой тестовой очереди.

Redis/AMQP не проверены: текущий адаптер отложенной аварийной доставки
рассчитан на DB-драйвер. Смена брокера требует отдельной реализации этого
контракта и решения атомарной постановки.

## Установка зависимости

Транспорт очередей — `yiisoft/yii2-queue`, объявлен в `composer.json` пакета.
Установить его в проекте:

```bash
composer update skeeks/cms-job --with-dependencies
```

Затем применить миграции:

```bash
php yii cms/migrate
```

Появятся таблица `cms_queue` (транспорт) и колонки `execution_token` в
`cms_job_run` и `cms_job_lock`.

## Один процесс — одна полоса

Перед настройкой служб получите полосы из итогового конфига проекта:

```bash
php yii cms-job/worker/queues
php yii cms-job/worker/queues --json
```

Команда показывает все зарегистрированные полосы, включая пустые, связанные
типы и максимальный TTR типов (`timeout + leaseSeconds`). Это не состояние
процессов и не количество сообщений: транспортные объекты не создаются, БД
командой не опрашивается. Пустая полоса имеет `max_ttr: null`.
JSON-контракт версии 1: `schema_version`, массив `queues` с `name`, `types`
(`type`, `title`, `timeout`, `ttr`) и `max_ttr`, массив `unconfigured_types`
с `type`/`queue`. Секреты и полный конфиг транспорта не выводятся.
Ссылка типа на отсутствующую полосу даёт код 78 и запись в
`unconfigured_types`; исправьте конфигурацию до настройки служб.
Список не включает неустановленные пакеты и не запускает воркеры автоматически.

```bash
php yii cms-job/worker --queue=imports
```

Это не стилистическое предпочтение. Импорт поставщика идёт часами; если тот же
процесс обслуживает уведомления, они ждут его окончания. Разные полосы
масштабируются независимо и падают независимо.

Список через запятую не поддерживается: команда отклонит его с подсказкой,
какие процессы запустить вместо этого.

### Опции

| Опция | Назначение |
| --- | --- |
| `--queue` | имя полосы, обязательно |
| `--once` | обработать доступное и выйти |
| `--idleDelay` | пауза при пустой очереди, сек |
| `--maxJobs` | остановиться после N заданий |
| `--maxSeconds` | остановиться через N секунд |
| `--memoryLimit` | остановиться при превышении N МиБ |

Пределы проверяются между заданиями и текущую операцию не прерывают. Плановый
перезапуск дешевле расследования утечки в процессе, живущем неделями.

### Коды возврата

| Код | Значение |
| --- | --- |
| 0 | штатная остановка, в том числе по сигналу и по пределам |
| 64 | полоса не указана, не настроена или передан список полос (`ExitCode::USAGE`) |
| 78 | перехваченная ошибка конфигурации транспорта (`ExitCode::CONFIG`) |

## Обычный хостинг: периодический cron

Публичная команда для хостинга без постоянных процессов:

```bash
php yii cms-job/worker/cron --queue=maintenance
```

Она использует тот же транспорт и изоляцию, что постоянный воркер, но не ждёт
новых или отложенных сообщений. Дефолты: `maxJobs=100`, `maxSeconds=50`,
`memoryLimit=256`. Опции можно переопределить положительными целыми числами;
ноль выбирает дефолт cron, а не снимает ограничение. `--once=0` не включает
ожидание у этой команды. Обычный `worker` и его `--once=1` остаются совместимыми.

Пример crontab (пути и PHP заменить на свои; запускать от пользователя сайта):

```cron
* * * * * /usr/bin/php /home/site/project/yii cms-job/worker/cron --queue=maintenance --maxSeconds=50 --maxJobs=100 --memoryLimit=256
```

На каждую нужную полосу — отдельная строка. Не включайте полосы без заданий.
Следите за выводом cron или направьте его в ротируемый журнал: отсутствие
воркера и ошибки загрузки приложения нельзя скрывать перенаправлением в null.

Команда неблокирующе захватывает локальный `flock` на всё время обработки.
Следующий cron той же полосы выходит с кодом 0 без потребления, если первый
ещё работает. Файлы блокировок находятся в
`@root/console/runtime/cms-jobs/locks`; настройка контроллера `cronLockPath`
позволяет изменить каталог. Он должен быть приватным, постоянным, доступным
пользователю сайта и одинаковым между запусками/релизами. Не удаляйте lock-файлы
при работающих процессах: блокируется inode, а не наличие файла. После аварии
ОС освобождает блокировку; дочерний exec её не наследует.

Это ограничитель cron на одном сервере, не распределённая блокировка заданий.
Разные полосы независимы. Постоянные воркеры эту блокировку не используют:
при смене режима сначала отключите прежний запуск и дождитесь его завершения.

Хостинг должен разрешать PHP CLI, `proc_open` и дочерние процессы, локальный
`flock`, доступ к БД и функции/расширения, нужные обработчикам. Для корректной
мягкой остановки Linux-воркера нужны `pcntl`/`posix`. Не отключайте изоляцию
автоматически, если хостер запретил процессы. HTTP-вызов вместо CLI не является
поддерживаемой заменой. Проверяйте ограничения CPU, памяти и времени у хостера.

**50 секунд — не жёсткий таймаут всего процесса.** Проверка идёт между
заданиями; начатая операция дорабатывается в пределах своего timeout/TTR.
Лимит процесса хостера должен иметь запас для этого. Длинные операции нужно
дробить и сохранять курсор; cron сам не превращает многочасовую команду в чанки.
Время ожидания пользователя зависит от частоты cron и накопленной очереди.
Команды `reap`, `cleanup` и `cleanup-logs` по-прежнему настраиваются отдельно.

## Ubuntu/VPS: systemd

Пример `/etc/systemd/system/cms-job-example-maintenance.service`.
Замените пользователя, каталог и PHP; пример рассчитан на задачи с TTR не
более 3600 секунд, иначе увеличьте время остановки:

```ini
[Unit]
Description=SkeekS example maintenance worker
After=network.target

[Service]
Type=simple
User=site-user
WorkingDirectory=/home/site/project
ExecStart=/usr/bin/php /home/site/project/yii cms-job/worker --queue=maintenance --maxSeconds=3600 --memoryLimit=256
Restart=always
RestartSec=5
KillSignal=SIGTERM
KillMode=mixed
TimeoutStopSec=3700
UMask=0007

[Install]
WantedBy=multi-user.target
```

`KillMode=mixed` отправляет TERM родителю, чтобы текущий дочерний процесс
доработал; после TimeoutStopSec systemd может принудительно остановить всю
группу. Время остановки должно превышать максимальный TTR с запасом.
`Restart=always` нужен и для штатного выхода по maxSeconds/maxJobs.

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now cms-job-example-maintenance.service
systemctl status cms-job-example-maintenance.service
journalctl -u cms-job-example-maintenance.service -n 50
```

Это пример установки администратором, а не действие пакета: приложение не
получает root. В OpenVZ предварительно проверьте работающий systemd внутри
VPS. Для каждого проекта/полосы — свой unit с пользователем и PHP этого сайта.
При обновлении отключите производителей, завершите работу воркеров до замены
кода, примените миграции, затем запустите службы и производителей снова.

## Supervisor

Числа ниже — пример, а не рекомендация пакета. Подбирать под нагрузку проекта.

```ini
[program:cms-job-imports]
command=php /app/yii cms-job/worker --queue=imports --maxSeconds=3600 --memoryLimit=512
numprocs=1
process_name=%(program_name)s
user=www-data
autostart=true
autorestart=true
stopsignal=TERM
; Больше, чем самая долгая порция: воркер дорабатывает текущее задание.
stopwaitsecs=600
redirect_stderr=true
stdout_logfile=/var/log/cms-job/imports.log

[program:cms-job-exports]
command=php /app/yii cms-job/worker --queue=exports --maxSeconds=3600 --memoryLimit=512
numprocs=1
user=www-data
autostart=true
autorestart=true
stopsignal=TERM
stopwaitsecs=600

[program:cms-job-notifications]
command=php /app/yii cms-job/worker --queue=notifications --maxJobs=500
numprocs=4
process_name=%(program_name)s_%(process_num)02d
user=www-data
autostart=true
autorestart=true
stopsignal=TERM
stopwaitsecs=60

[program:cms-job-mail]
command=php /app/yii cms-job/worker --queue=mail --maxJobs=500
numprocs=2
process_name=%(program_name)s_%(process_num)02d
user=www-data
autostart=true
autorestart=true
stopsignal=TERM
stopwaitsecs=120

[program:cms-job-hosting]
command=php /app/yii cms-job/worker --queue=hosting --maxSeconds=3600
numprocs=2
process_name=%(program_name)s_%(process_num)02d
user=www-data
autostart=true
autorestart=true
stopsignal=TERM
stopwaitsecs=900
```

Почему такие числа в примере: импорт и экспорт держат ресурс целиком, второй
процесс всё равно упрётся в блокировку — им хватает одного. Уведомления и
почта состоят из множества коротких заданий, они выигрывают от нескольких
процессов. Хостинг ограничен внешним API провайдера.

`stopwaitsecs` обязан превышать длительность самой долгой операции полосы,
иначе Supervisor добьёт процесс сигналом KILL посреди работы. Задание при этом
не потеряется — его подберёт уборка по истёкшей аренде, — но неидемпотентная
операция окажется в статусе `timed_out` с неизвестным результатом.

## Docker Compose

```yaml
services:
  worker-imports:
    build: .
    command: php /app/yii cms-job/worker --queue=imports --maxSeconds=3600 --memoryLimit=512
    restart: unless-stopped
    stop_signal: SIGTERM
    stop_grace_period: 600s
    depends_on: [db]

  worker-notifications:
    build: .
    command: php /app/yii cms-job/worker --queue=notifications --maxJobs=500
    restart: unless-stopped
    stop_signal: SIGTERM
    stop_grace_period: 60s
    deploy:
      replicas: 4
    depends_on: [db]
```

`stop_grace_period` играет ту же роль, что `stopwaitsecs`: по умолчанию Docker
даёт 10 секунд, чего долгой операции не хватит.

## Плановое обслуживание

Возврат зависших запусков и снятие брошенных блокировок — раз в несколько
минут:

```bash
php yii cms-job/worker/reap
```

Удаление прогонов с истёкшим сроком хранения — раз в сутки:

```bash
php yii cms-job/worker/cleanup
```

Обе команды короткие и безопасны при параллельном запуске.

## Диагностика

### Приватные логи

Новые артефакты `log` и `error-report` не загружаются в `cms_storage_file` / uploads.
Компонент `jobLogs` хранит их в приватной папке. В SkeekS конфиг пакета
использует `@root/console/runtime/cms-jobs/logs`: обычный `@runtime` различается у
web и console. Для другого расположения задайте **одинаковый** `basePath`
в общем конфиге обоих приложений:

```php
'components' => [
    'jobLogs' => [
        'basePath' => '@root/console/runtime/cms-jobs/logs',
        'maxBytes' => 5 * 1024 * 1024,
        'retentionDays' => 14,
    ],
],
```

Структура: `maintenance/2026/09/07/0/979-<random>.log`.
Отчёты об ошибках используют тот же путь с расширением `.csv`, срок хранения
и команды очистки. CSV сохраняется полностью: `maxBytes` ограничивает только
консольные логи. Каждое продолжение задания сохраняет отдельный фрагмент отчёта
с уникальным именем; старый воркер не может затереть файл нового продолжения.
Дата — UTC; группа — `intdiv(runId, 1000)`. На одну дату/группу приходится
до 1000 ID, но повторные попытки создают отдельные файлы. Вывод консольной
команды ограничен 5 МиБ с отметкой об усечении; чтение stdout/stderr после
лимита продолжается, чтобы не заблокировать дочерний процесс.

Перед обновлением остановите workers, примените новую миграцию артефактов,
затем перезапустите workers. Каталог должен быть вне document root, на общем
постоянном томе web/worker/cleanup. Для нескольких серверов нужен общий
filesystem либо отдельная реализация хранилища. Unix-пользователи должны
совпадать или иметь общую группу: каталоги 2770, файлы 0660; для наследования
группы задайте setgid на корневом каталоге. Не отдавайте эту папку nginx.

Скачивание идёт через авторизованный backend action с проверкой сайта и прав
на тип задания; ответ приватный, без кеширования. Лог регистрируется до
запуска команды, поэтому доступен и после аварии. Активные логи не удаляются.

Запускайте каждый час (частоту подберите по объёму):

```bash
php yii cms-job/worker/cleanup-logs
```

Один проход удаляет до 500 просроченных логов завершённых заданий и до 500
старых файлов без метаданных. Возраст последних определяется по mtime;
незавершённые прогоны защищены. Срок обычного лога отсчитывается от создания
артефакта. Метаданные и история сохраняются отдельно; после очистки интерфейс
показывает, что лог истёк. Команда `cleanup` истории тоже удаляет связанные
приватные логи перед удалением строк (до 500 прогонов за проход).

Исключите `console/runtime/` (или `console/runtime/cms-jobs/logs/`) из файлового бэкапа и контролируйте
место на диске/выполнение очистки. Сам перенос не меняет настройки бэкапа.
Старые логи и отчёты в CMS storage автоматически не переносятся
и не удаляются. Результаты экспорта и исходные файлы используют CMS storage;
их срок хранения и физическую очистку нужно обслуживать отдельно.

```bash
php yii cms-job/worker/push console.command '{"command":"help"}'
php yii cms-job/worker --queue=maintenance --once
```

Что смотреть при разборе:

- **очередь не разбирается** — проверить, что процесс слушает нужную полосу:
  полоса задания берётся из реестра типов, а не из места вызова;
- **задание висит в `running`** — сравнить `lease_until` с текущим временем;
  просроченную аренду разбирает `reap`;
- **`timed_out` вместо повтора** — тип не объявлен идемпотентным, и ядро
  намеренно не повторяет операцию с неизвестным результатом;
- **постановки молча пропадают** — сработала политика пересечения; факт
  фиксируется счётчиком `skipped_runs` на активном прогоне, а не теряется.

Транспортная таблица историей не является: после успешной обработки сообщение
удаляется. История операции целиком в `cms_job_run`.

## Мягкий перезапуск

```bash
supervisorctl restart cms-job-imports
docker compose up -d --force-recreate worker-imports
```

SIGTERM останавливает цикл между заданиями: текущая операция дорабатывается,
новая не берётся. Прерывать выполняющуюся операцию сигналом нельзя — для этого
есть отмена, которая доводится до обработчика штатно.
