# Рабочие папки заданий

Для временных исходников, распаковки и промежуточных результатов используйте
JobContext. Новому обработчику не нужна своя команда очистки:

```php
public function run(JobContext $context, JobReporterInterface $reporter): void
{
    $workspace = $context->getWorkspace();
    $file = $workspace->path('offers.jsonl');
    // Записать/прочитать файл. Соблюдать курсор и heartbeat обычного обработчика.
}
```

`path()` без аргументов возвращает каталог данных для библиотек, которым нужен
путь к папке. Относительное имя может содержать вложенные каталоги; создать
их должен обработчик. Для имён через path используйте ASCII-буквы, цифры,
точки, дефисы и подчёркивания. Абсолютные пути, обход через .. и ссылки запрещены.

## Место хранения и владельцы

По умолчанию в конфиге SkeekS:
`@root/console/runtime/cms-jobs/workspaces/runs/<cms_job_run.id>/data/`.

Рядом с data пакет хранит manifest.json и файловую блокировку. Не изменяйте
служебные файлы. У одного запуска одна папка независимо от числа доставок,
автоматических повторов и перезапусков процесса. Ручной повтор с новым run ID
получает новую папку и не наследует исходники автоматически.

```php
'components' => [
    'jobWorkspaces' => [
        'basePath' => '@root/console/runtime/cms-jobs/workspaces',
        'successDays' => 7,
        'failureDays' => 14,
    ],
],
```

Корень должен быть приватным, вне document root, одним и тем же для web,
воркеров и очистителя. Процессы должны работать под одним Unix-пользователем:
создаваемые каталоги имеют режим 0700. Не меняйте корень при наличии данных
без отдельного переноса: иначе очиститель потеряет видимость старых ресурсов.
Миграций БД нет.

Логи/CSV об ошибках по-прежнему создавайте через reporter/артефакты.
Постоянные выгрузки, пользовательские загрузки и общий кеш нескольких job
храните отдельно. Не передавайте workspace дочерним заданиям и не запускайте
отсоединённых писателей: владение заканчивается при выходе из run().

## Блокировки и продолжения

При первом обращении к workspace проверяются свежий running-статус,
execution_token и срок аренды. Контекст держит flock до выхода обработчика;
runner освобождает его в finally при успехе, ошибке, отмене и requeue.
Истёкший DB lease не снимает физическую блокировку живого старого процесса.
Новый исполнитель того же запуска ждёт посредством requeue, не расходуя
попытку. Каждый вызов path дополнительно проверяет владение.

Между доставками папка защищена незавершённым статусом. Не вызывайте
releaseWorkspace/close самостоятельно; не сохраняйте объект или путь для
работы после возврата обработчика. Уже открытые файлы доступны старому процессу,
но его lock не позволяет очистителю удалить папку или новому исполнителю её
использовать. Это протокол сотрудничающих процессов, а не песочница против
скомпрометированного кода с теми же правами.

Поддерживаемая конфигурация — локальная ФС с согласованным flock и атомарным
rename. Несколько независимых дисков, NFS и объектное хранилище не поддержаны
без отдельной проверки/реализации протокола. Общий каталог в NFS сам по себе
не является доказательством безопасной блокировки.

## Хранение и автоматическая очистка

Системная job `cms-job.cleanup-workspaces` зарегистрирована на maintenance
раз в час. После установки загрузите расписания через `php yii cmsAgent/init`
и мягко перезапустите воркеры; нужны работающий scheduler и потребитель.
Ручной запуск доступен в «Расписании», как для остальных системных job.

Срок отсчитывается от finished_at:
- succeeded: 7 суток;
- succeeded_with_warnings, failed, cancelled, timed_out: 14 суток;
- queued/running: не удаляются независимо от возраста;
- hold, отсутствующая история, неизвестный манифест или небезопасные файлы:
  сохраняются для проверки.

Сначала очиститель берёт общую блокировку каталога и блокировку конкретной
папки, перечитывает владельца и состояние. Затем проверяет всё дерево,
переименовывает его в trash на той же ФС и удаляет без перехода по ссылкам.
Данные не копируются, поэтому операция не требует второго объёма свободного
места. Карантин не имеет дополнительного срока ожидания. Журнал удаления
сохраняется до последнего rmdir и позволяет продолжить после остановки
процесса. Symlink, hardlink, специальные файлы и смена inode приводят к пропуску.

Один проход рассматривает до 100 папок, затем продолжает со следующего ID.
Защитные пределы одного дерева: 20 000 элементов и глубина 32; превышение
выводится как ошибка, ничего из этого дерева не удаляется. Между папками
действует предел 30 секунд. Обход списка ID и одного дерева может занять больше
времени на медленной ФС; heartbeat и отмена проверяются во время обхода.
Глобальная блокировка открывается ненадолго, но полный предварительный обход
одной папки под ней может отложить обращения других job.

История не удаляется штатным cleanup и через модель, пока существует папка
или журнал её удаления. Transient-job, использовавшая workspace, сохраняет
терминальную запись для обслуживания ресурса. Прямой SQL/deleteAll вне штатных
сервисов обходит модельную защиту: такие записи считаются неоднозначными,
папки по ним не удаляются автоматически.

## Расчёт без удаления и ручное обслуживание

```bash
# dryRun=1, limit=100, after=0 — значения по умолчанию
php yii cms-job/worker/cleanup-workspaces

# Следующая страница: значение after из предыдущего ответа
php yii cms-job/worker/cleanup-workspaces 1 100 12345

# Фактическая очистка одной страницы, с повторной проверкой всех условий
php yii cms-job/worker/cleanup-workspaces 0 100 0

# Удержать завершённую папку для разбора, затем снять удержание
php yii cms-job/worker/workspace-hold 12345 1
php yii cms-job/worker/workspace-hold 12345 0
```

Dry-run не создаёт каталогов и служебных файлов, открывает существующие lock
файлы только для чтения и берёт неблокирующие locks. Результат — снимок,
а не разрешение удалить папку позже без проверки. Ответ содержит ID, статус,
возраст, причину решения и логический объём проверенных кандидатов. Объём
необследованных/занятых папок не измеряется; ноль в таком элементе не означает
пустую папку. Реальное освобождение блоков проверяется через df/du.

Для планового прохода сохраняются суммарные счётчики, причины пропуска и
предупреждения. Контролируйте отсутствие успешных запусков, unsafe_or_error,
missing_run, unknown completion, неизвестные элементы и рост удержанных папок.
Ошибочные папки не препятствуют проверке последующих ID.

## Переход со старых проектных папок

Чужие runtime-каталоги не усыновляются автоматически. Проект явно указывает
корни старых папок, именованных ID запуска, только для защиты истории:

```php
'jobWorkspaces' => [
    'historyProtectionRoots' => ['@root/console/runtime/supplier-imports'],
],
```

Эта настройка не разрешает удаление старых снимков. Новые импорты используют
getWorkspace; старые продолжают читать прежний путь до завершения. Отдельная
инвентаризация и согласованная процедура очистки/переноса необходимы для старых
папок, особенно если прежние исполнители ещё не используют файловый lock.
После их подтверждённого удаления защиту старого корня можно убрать.

Перед развёртыванием синхронно обновите пакет, проектный адаптер и воркеры.
Старый cms-job без JobContext::getWorkspace не совместим с новым адаптером.
Не откатывайте пакет на старую очистку истории при наличии managed workspaces;
сначала отключите очистку истории и определите судьбу ресурсов.
